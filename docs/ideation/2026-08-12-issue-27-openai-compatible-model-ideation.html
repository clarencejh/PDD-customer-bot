Issue #27 + OpenAI-compatible model support

把 DeepSeek 的 400 参数兼容问题，收敛成一个更稳的连接边界：portable by default，供应商扩展显式启用，用户可以输入任意兼容端点和原始模型 ID。

Date 2026-08-12 Topic issue-27-openai-compatible-model Mode repo-grounded

Grounding Context

Codebase Context

  • LLMConfig 目前只有 model_name、api_key、api_base；设置页已有这三个输入，但默认值偏向 Volcengine/Doubao。
  • AsyncOpenAI 已支持自定义 base_url，真正的耦合发生在发送前导入并实例化 Volcengine 专用请求模型。
  • model_dump(exclude_none=True) 会把 logprobs、top_logprobs、service_tier 等非 None 默认值发到任意端点。
  • 现有测试使用 unittest 和 mock，但没有请求序列化、兼容策略、Base URL 或不支持参数的回归测试。

Issue Context

  • Issue #27 报告 DeepSeek 自动回复因 logprobs=false、top_logprobs=0 返回 400。
  • 当前 issue 仍为 Open，没有关联 PR；修复应覆盖同类供应商参数泄漏，而不是只删掉两个字段。
  • 用户希望同时获得方便的自定义模型入口，因此“兼容请求边界”和“配置体验”需要一起设计。

External Context

  • OpenAI Python SDK 支持自定义 base_url 和显式的 extra_body 等扩展入口。
  • Open WebUI 将连接身份与模型 ID 分开，并允许在模型发现不可用时手动输入模型。
  • LiteLLM 等方案说明：OpenAI-compatible 是传输形状，不代表所有可选参数都兼容。

Decision Pressure

  • 最小修复是把 provider-specific defaults 变成显式配置；更长期的价值是让新增端点不再需要改聊天主循环。
  • 用户不应被强迫填写 provider 名称才能使用一个兼容端点；原始模型 ID 和 Base URL 应成为一等配置。
  • 模型发现和连通性检查应当提升便利性，而不能阻断合法的手动配置。

1. Portable request core with explicit provider extensions

Axis
Request compatibility boundary
Confidence
96%
Complexity
Medium
Shape
Core boundary
Description

把发送边界从 Volcengine 专用的 ChatCompletionsRequest 换成 provider-neutral 的请求形状，只发送代理明确设置的 model、messages、temperature 和实际使用的 tools。service_tier、reasoning_effort、logprobs、top_logprobs 等供应商扩展进入显式 extension lane，不能通过 schema 默认值泄漏到任意端点。

Basis

direct: llm_client.py:103-135 先构造小请求再发送完整 model dump；volcengine_models.py:248-263 给供应商字段设置了非 None 默认值。

Rationale

这不仅删掉 #27 的两个字段，还阻断同一类未来泄漏；“兼容端点”首先得到一个最小、可预测的请求。

Downsides

需要明确哪些参数属于真正的 portable core，并把当前 Volcengine 行为拆到显式扩展层。

2. Capability policy and adapter boundary per connection

Axis
Request compatibility boundary
Confidence
90%
Complexity
Medium
Shape
Policy boundary
Description

为连接增加一个小而可审计的兼容策略，例如默认 portable 和保留现有行为的 volcengine_legacy。策略是可选字段的 allow-list，而不是继续扩张 provider 分支；模型发现、预设和特殊参数也作为可选 adapter 叠加在同一个 portable client 上。

Basis

direct: config.py:24-37 有 provider 枚举却没有运行时 provider 字段，llm_client.py:16-17 直接导入 Volcengine 请求模型。reasoned: OpenAI-compatible 代表协议交集，不代表每个可选参数都被支持。

Rationale

它让兼容性从隐式继承变成显式、可解释的连接属性，同时避免为每个新端点重写聊天主循环。

Downsides

策略词汇必须保持小规模；如果做成完整能力矩阵，维护成本会重新失控。

3. One active connection profile, separate from the raw model ID

Axis
Connection and model configuration
Confidence
87%
Complexity
Medium
Shape
Configuration UX
Description

把现有三字段解释成一个明确的 active connection profile：名称、规范化 Base URL、受保护的 key、兼容策略；当前模型仍是独立的原始 model ID。v1 只保留一个 active profile，并迁移当前 Doubao/Ark 配置不变；多 profile 切换留到后续。

Basis

direct: config.py:32-37 目前只有三个匿名 LLM 字段，而 llm_client.py:64-70 已接受自定义 Base URL。external: Open WebUI 将连接身份与模型身份分开。

Rationale

用户无需先理解 provider 枚举就能输入任意 endpoint 和模型 ID，同时不会把“哪里连接”和“调用什么模型”混成一个概念。

Downsides

即使只做一个 active profile，也需要谨慎迁移旧 JSON 和调整设置页文案；多连接管理不应被 v1 偷渡进来。

4. Best-effort model discovery with manual IDs first-class

Axis
Settings and user experience
Confidence
88%
Complexity
Medium
Shape
Progressive setup
Description

在 endpoint 和 key 可用后提供“测试并发现模型”，把返回的 model IDs 作为建议并按连接缓存；当 /models 不存在、受限或格式不同，仍允许用户直接输入模型 ID。发现是便利增强，不是配置真相。

Basis

external: Open WebUI 的兼容端点指南将连接与手动模型配置分开。direct: 当前设置页已经有 model name 输入，但没有 discovery 路径。

Rationale

常见端点可以减少模型名猜测，企业网关和非标准服务也不会因为缺少 discovery 而被排除。

Downsides

需要处理缓存、刷新、超时和 discovery 失败的状态；保存不能依赖远程服务在线。

5. Endpoint normalization and non-blocking preflight

Axis
Settings and user experience
Confidence
91%
Complexity
Medium
Shape
Setup feedback
Description

规范化用户粘贴的 Base URL，校验 URL 形状并提示重复的 /v1 或 /api/v3 路径；提供有超时的最小 preflight，把 malformed URL、无法连接、认证失败、endpoint 形状不对和 discovery 不可用区分开。discovery 不支持时仍可保存。

Basis

direct: setting_ui.py:46-50、72-84 和 443-449 偏向 Volcengine 默认且只检查 key/model。external: OpenAI SDK 有 Base URL 处理，Open WebUI 对 discovery 失败采取非阻断策略。

Rationale

把“保存后等自动回复报 400”变成设置阶段可行动的反馈，尤其能降低自定义网关的接入成本。

Downsides

网络检查必须有清晰的错误分类和短超时，不能把远程波动变成保存配置的硬门槛。

6. Pure request builder plus compatibility contract matrix

Description

抽出纯 request builder，并为 portable、legacy、DeepSeek-compatible 三类输出建立 fixture。测试精确的 outgoing keys，尤其要求 portable 请求中不存在 logprobs、top_logprobs、service_tier、reasoning_effort 等未经请求的字段；同时覆盖旧配置迁移和 URL 规范化。

Downsides

portable contract 变更时需要维护 fixtures；这些测试不替代少量真实 endpoint 的集成验证。

7. Sanitized compatibility fingerprint for actionable failures

Axis
Settings and user experience
Confidence
86%
Complexity
Medium
Shape
Supportability
Description

在设置测试和 provider 4xx 诊断中记录 endpoint origin、raw model ID、active policy、操作类型、HTTP status 和发送字段名，但绝不记录 API key、prompt 或客户消息。客户仍收到安全的通用兜底，运营侧则能复制一份可复现的脱敏 fingerprint。

Basis

direct: customer_agent.py:291-305 将 LLM 错误折叠成通用提示，而 llm_client.py:114-122 仅记录验证异常类型。

Rationale

随着自定义端点增多，支持团队需要区分 URL、认证、模型和参数兼容性，而不是让所有失败都看起来像临时服务不可用。

Downsides

脱敏边界必须严格；field names 和 endpoint origin 也应避免携带 query 中的 secret。
